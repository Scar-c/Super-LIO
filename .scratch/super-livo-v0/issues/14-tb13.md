# 14: [Super-LIVO v0][TB-13] Finalize geometry and visual map update ordering

**Status:** ready-for-agent

## Parent

本地 tracker parent：`00-parent.md`（Super-LIVO v0 — Camera-Epoch Sequential LIVO with Common-FEJ）

## Source specification

`docs/super_livo/specs/super_livo_v0_spec.md` → **TB-13 节**、**Dataflow 节**、ADR-006（DECISION-18）。

## Goal

最终确定 geometry + visual map update 顺序：当前 epoch geometry 必须以 VIO 后最终状态 x_LC 插入，防止"先以 x_L 插图、随后 VIO 改变 pose"造成的 map inconsistency。

## Why this tracer bullet exists

DECISION-18：地图插入必须在 LIO→VIO→final state 之后；这是 ADR-001 epoch 语义的收尾，保证 geometry 与视觉共享同一最终状态。

## What to build

最终 epoch 顺序（全模式）：

```text
IMU propagation
  → LiDAR nonlinear search
  → common anchor
  → final LIO update
  → VIO
  → x_LC
  → GeometryMap update（用 x_LC）
  → VisualMap update
```

- 插入 pose 与最终发布 pose 一致的断言/诊断。
- TB-5 eviction 联动在全模式下生效验证。

## Explicit non-goals

- 不改地图结构 / LRU 语义 / eviction 触发条件。
- 无新算法；无 adaptive noise；无 camera-only。

## Architectural invariants

- I-10：Geometry map insertion 发生在 VIO final state 之后。
- ADR-006 DECISION-18。

## Likely code seams

- orchestrator（`livo/`）UpdateMap 调用点顺序。

## Tests required

- component（顺序断言）+ dataset（全模式无 map 损坏）。

## Acceptance criteria

- [ ] 当前 epoch geometry 插入使用的 pose == VIO 后最终状态 x_LC（component 断言：插入时读到的 pose 与最终发布 pose 一致）。
- [ ] 代码路径中不存在"geometry 以 x_L 插入后再被修改"的顺序（review + 日志/顺序断言佐证）。
- [ ] TB-5 的 eviction 联动在 livo_common_fej 全模式下生效（TB-5 测试扩展，automated）。
- [ ] MODE-A/B/C dataset 运行后 map 无损坏（map_stats 一致、无孤儿 key）。
- [ ] 最终发布 trajectory 的时间戳与状态来自 x_LC 之后的输出（一致性断言）。

## Runtime / memory / debug artifacts

- map_stats.csv（插入计数、eviction 联动计数）。

## Failure rules

- FAIL：插入早于 VIO final、插入 pose ≠ x_LC、eviction 联动失效。
- 允许改：orchestrator 内部顺序。
- 禁止用于救场：把 map 更新挪回 x_L 时刻。
